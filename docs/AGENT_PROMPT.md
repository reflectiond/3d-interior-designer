## Правила работы (наследуются из фазы v0.x — v1.0)

### 1. Git-дисциплина

- Никогда не коммитить напрямую в `main`.
- Каждая фича — отдельная ветка `feature/<scope>-<short-name>`. Для багфиксов — `fix/<short-name>`.
- Conventional Commits на английском: `feat:`, `fix:`, `chore:`, `docs:`, `test:`, `refactor:`.
- PR описывается на русском, содержит: ссылку на ID требования из спецификации, скриншоты UI-изменений (для визуальных правок — **обязательно**), чек-лист тестов.
- Squash merge.
- При завершении спринта — semver-тег и GitHub Release с changelog'ом.

### 2. После каждого тега обязательно:

- Обновить `docs/PROGRESS.md` — статус каждого затронутого требования (✅ Done / 🚧 In Progress / ⏳ Planned / ❌ Blocked).
- Если в ходе разработки обнаружено уточнение — внести правки в `docs/SPECIFICATION.md` с пометкой `Уточнено в vX.Y.Z: …`.
- Если принято существенное архитектурное решение — добавить ADR в `docs/DECISIONS.md`.
- Создать GitHub Release с changelog'ом.

### 3. Качество кода

- TypeScript strict mode. `any` запрещён без обоснования в комментарии.
- ESLint + Prettier обязательны, pre-commit hook через Husky уже настроен.
- Каждая чистая функция в `src/domain/` покрывается unit-тестом.
- Каждое функциональное требование (F-ID) покрывается e2e-тестом, если оно меняет поведение UI.
- Каждое security-требование (SEC-ID) покрывается e2e-тестом в `tests/e2e/security.spec.ts`.

### 4. Архитектурные принципы

- **Один источник правды:** Zustand-стор содержит весь проект. Не дублировать данные в локальных стейтах компонентов.
- **Никаких хардкоженных цветов в компонентах.** Только импорт из `src/theme/palette.ts`. Палитра расширена для v1.x (см. SPECIFICATION §3.4) — используй новые ключи.
- **Чистая логика отделена от UI:** всё, что в `src/domain/`, не импортирует React, Konva, Three.js. Это позволяет 100% покрытие unit-тестами.
- **Тайлы — целые числа.** Преобразование в метры — только на границе.

### 5. Безопасность

- Никаких `dangerouslySetInnerHTML` без DOMPurify.
- Все импортируемые JSON валидируются через Zod-схемы.
- localStorage читается через try-catch с fallback на дефолт.
- Имена файлов экспорта санитизируются (см. F10.4.x).

### 6. Когда что-то неясно

- Если требование в спецификации неоднозначно или противоречит другому — **остановиться, написать issue** на GitHub с тегом `clarification-needed`. Не догадываться.
- Если есть два разумных способа реализации — описать оба в PR и попросить ревью.
- Не добавлять фич, которых нет в спецификации, без согласования.

## Детальный план первого спринта (v1.1.0)

### Подспринт 1.1.a — PT Sans в PDF (F10.1.x)

1. Скачать PT Sans Regular и Bold с Google Fonts (или с https://www.paratype.ru/), лицензия SIL OFL 1.1.
2. Положить файлы в `public/fonts/PT_Sans/`:
   - `PTSans-Regular.ttf`
   - `PTSans-Bold.ttf`
   - `OFL.txt` (копия лицензии)
3. Сгенерировать base64-представления шрифтов (через `node -e "console.log(require('fs').readFileSync('PTSans-Regular.ttf').toString('base64'))"`) и положить в `src/export/fonts/ptSans.ts` как именованные экспорты `PT_SANS_REGULAR_B64`, `PT_SANS_BOLD_B64`.
4. В `src/export/pdfExporter.ts` — на старте функции экспорта зарегистрировать шрифты в jsPDF:
   ```typescript
   doc.addFileToVFS('PTSans-Regular.ttf', PT_SANS_REGULAR_B64);
   doc.addFont('PTSans-Regular.ttf', 'PTSans', 'normal');
   doc.addFileToVFS('PTSans-Bold.ttf', PT_SANS_BOLD_B64);
   doc.addFont('PTSans-Bold.ttf', 'PTSans', 'bold');
   doc.setFont('PTSans', 'normal');
   ```
5. Заменить все `doc.setFont('helvetica', ...)` на `doc.setFont('PTSans', ...)`.
6. Unit-тест: `tests/unit/pdf-fonts.test.ts` — мокаем jsPDF, проверяем что `addFont` был вызван дважды.
7. E2E-тест E2E-10 в `tests/e2e/export.spec.ts`:
   ```typescript
   import * as pdfjsLib from 'pdfjs-dist';
   // ... сгенерировать PDF, прочитать textContent, проверить, что 'Стяжка пола' содержится в извлечённом тексте
   ```

**PR:** `feat(pdf): add PT Sans cyrillic font (F10.1.x)`

### Подспринт 1.1.b — Скриншоты 2D и 3D в PDF (F10.2.x)

1. Изучить текущий `pdfExporter.ts`. Понять, что сейчас рендерится только заголовок (см. `interior-project.pdf` — на стр. 1 и 2 нет картинок).
2. Реализовать `capture2DSnapshot()` в `src/export/snapshots.ts`:
   - Найти Konva.Stage через ref/глобальный store
   - Вызвать `stage.toDataURL({ pixelRatio: 2, mimeType: 'image/png' })`
   - Вернуть data URL
3. Реализовать `capture3DSnapshot()`:
   - Принимает props для камеры (фиксированная позиция, чтобы тест был детерминированным)
   - Внутри R3F: `useThree(({ gl, scene, camera }) => ...)` или императивный рендер через `gl.render(scene, camera); gl.domElement.toDataURL('image/png')`
   - Для рендера использовать дополнительный canvas в памяти, чтобы не дёргать UI пользователя
4. В `pdfExporter.ts` собрать 3 страницы:
   - Стр. 1: заголовок «3D Interior Designer — План 2D» (PTSans bold 14 pt) + изображение 2D
   - Стр. 2: заголовок «3D Interior Designer — Вид 3D» + изображение 3D
   - Стр. 3: заголовок «3D Interior Designer — Смета» + смета (плоская в этом спринте; группировка появится в v1.3)
5. Размер страницы — A4 landscape (297×210 мм). Изображения вписываются с отступами 10 мм по краям.
6. E2E-тест в `tests/e2e/export.spec.ts`: PDF имеет ровно 3 страницы, на каждой странице есть встроенное изображение (через `pdfjsLib.getDocument(...).getPage(n).getOperatorList()` — проверить наличие операторов рисования).

**PR:** `feat(pdf): embed 2D and 3D snapshots into PDF (F10.2.x)`

### Подспринт 1.1.c — PNG-экспорт (F10.3.x)

### Подспринт 1.1.d — Безопасные имена файлов (F10.4.x, SEC-8)

1. Утилита `src/export/sanitizeFilename.ts`:
   ```typescript
   export function sanitizeFilename(raw: string, fallback = 'untitled'): string {
     const cleaned = raw.replace(/[^a-zA-Z0-9_-]/g, '_').slice(0, 64);
     return cleaned.length > 0 ? cleaned : fallback;
   }
   ```
2. В `pdfExporter.ts` и `imageExporter.ts`: имя файла = `interior_design_${sanitizeFilename(projectId)}_${timestamp}.{pdf|png}`.
3. Unit-тест: 8+ кейсов (XSS, кириллица, пустая строка, длинные строки, спецсимволы пути).
4. E2E SEC-8: ввести имя проекта `<script>alert(1)</script>` → экспортировать → имя скачанного файла санитизировано.

**PR:** `feat(export): sanitize export filenames (F10.4.x, SEC-8)`

## Чего НЕ делать

- Не писать код, не относящийся к текущему спринту.
- Не добавлять зависимости вне списка в спецификации без обсуждения. Допустимо добавить: `pdfjs-dist` (только в devDependencies для тестов) — потому что нужно для E2E-10.
- Не использовать AI-генерируемые ассеты (3D-модели, иконки) без проверки лицензии.
- Не переписывать спецификацию по своему усмотрению — только дополнять с пометкой `Уточнено в vX.Y.Z: …`.
- Не пропускать тесты, чтобы быстрее замержить — лучше открыть issue или отложить требование с пометкой в `PROGRESS.md`.
- Не оптимизировать преждевременно. Сначала корректность, потом тесты, потом оптимизация при необходимости.
- **Не пытаться делать v1.2–v1.7 параллельно или вне очереди.** Идти строго по дорожной карте.
