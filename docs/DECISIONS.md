## ADR-001 — Загрузка PT Sans для PDF: lazy fetch вместо base64 в коде

**Дата:** 2026-04-27
**Версия:** v1.1.0
**Статус:** Принят

### Контекст

Спецификация v1.1 (раздел 4.10.1, F10.1.2) предписывает встраивать PT Sans Regular + Bold в PDF через хранение base64-строк в `src/export/fonts/ptSans.ts` и регистрацию в jsPDF при экспорте. Размер двух TTF-файлов после base64-кодирования — около 700 KB. Это попадает в основной JS-бандл и грузится при каждом старте приложения, даже если пользователь не дойдёт до экспорта PDF (а большинство пользователей не дойдут до экспорта в первой сессии).

### Решение

Хранить TTF-файлы как обычные ассеты в `public/fonts/PT_Sans/` и подгружать их через `fetch()` при первом вызове `exportPDF()`. Реализация в `src/export/fonts/ptSans.ts` с модульным кешем — повторные вызовы экспорта не делают дополнительных запросов.

### Последствия

**Плюсы:**

- Основной JS-бандл не вырастает на ~700 KB.
- Стартовая загрузка приложения остаётся в пределах нефункционального требования 5.1 (< 3 с на 4G).
- Браузерный HTTP-кеш покрывает повторные сессии естественно.

**Минусы:**

- Первый клик «Сохранить как PDF» добавляет асинхронную задержку ~100–300 мс на загрузку шрифтов (в зависимости от соединения). Последующие клики мгновенны.
- Нужна корректная отдача `public/` Vite/хостингом — стандартное поведение, без особенностей.
- E2E-тест должен дождаться окончания асинхронной загрузки шрифтов перед проверкой PDF.

### Альтернативы, которые рассмотрены

1. **Base64 в коде (как в спецификации).** Отклонено из-за роста бандла.
2. **CDN (Google Fonts).** Отклонено: внешняя зависимость противоречит CSP `default-src 'self'` (нефункциональное требование 5.3).
3. **WOFF2 вместо TTF.** jsPDF понимает только TTF/OTF, WOFF2 не поддерживается.

### Уточнение в спецификации

В `docs/SPECIFICATION.md` пункт F10.1.2 — добавлена пометка `Уточнено в v1.1.0: lazy fetch вместо base64 (см. ADR-001)`.

## ADR-002 — Редактор планировок: нет отдельного wall-инструмента

**Дата:** 2026-04-27
**Версия:** v1.6.0
**Статус:** Принят

### Контекст

Спецификация v1.6 (F11.2.2) описывает инструмент «Стена» — рисование межкомнатных и внешних стен кликом по граням тайлов. Однако `LayoutSchema` (`src/domain/geometry/types.ts`) не хранит стены как отдельные сущности: стены выводятся из прямоугольников комнат (внешний контур = периметр объединения, внутренние = общие грани соседних комнат). Аналогичная схема используется во `View2D` и в 3D-сцене.

### Решение

В редакторе планировок v1.6.0 не делать отдельного wall-инструмента. Набор инструментов: «Выбор», «Комната» (drag прямоугольника), «Электрощиток» (клик), «Окно» (два клика вдоль грани), «Дверь» (то же + параметры hinge/swing_side).

Стены автоматически восстанавливаются из `rooms[]` при загрузке layout JSON в основное приложение — никакой ручной отрисовки не требуется.

### Последствия

**Плюсы:**

- Редактор экспортирует JSON, который непосредственно соответствует `LayoutSchema` без преобразований.
- Меньше состояний: пользователь не может случайно нарисовать стену, не принадлежащую ни одной комнате.
- Меньше валидаций: «контур замкнут» сводится к «комнаты не оставляют дыр».

**Минусы:**

- Невозможно сделать комнаты сложной формы (L, T) без нескольких rectangle-rooms, как уже принято в layout1/2/3.
- Если в v2.0 потребуется сложная геометрия — модель данных и редактор расширяются одновременно.

### Уточнение в спецификации

В `docs/SPECIFICATION.md` пункт F11.2.2 — добавлена пометка `Уточнено в v1.6.0: wall-инструмент отсутствует, стены выводятся из rooms (см. ADR-002)`.

## ADR-003 — Графические ассеты мебели: PNG-спрайты + glTF-модели

**Дата:** 2026-04-30
**Версия:** v1.16.0

### Контекст

До v1.15.0 мебель рендерилась плоскими прямоугольниками с цветной заливкой (2D, Konva `Rect`) и box-геометрией с `meshStandardMaterial` (3D, R3F). Это компактно и быстро, но визуально неинформативно — диван и стол отличаются только цветом.

Спринт 21 добавляет визуально-богатые ассеты, не ломая существующий рендер.

### Решение

1. **Каталог расширяется опциональными полями** (`CatalogItem`, `src/domain/furniture/placement.ts`):
   - `sprite2d?: string` — путь к PNG (top-down view) для 2D-канвы.
   - `model3d?: { url: string; rotation?: number; scaleY?: number }` — glTF/GLB для 3D.
   - Оба поля **опциональны**: при отсутствии работает текущий цветной fallback.

2. **2D — Konva `Image` через lazy-load `<img>`** (хук `useLazyImage`):
   - При наличии `sprite2d` создаётся `HTMLImageElement`, после `onload` рендерится Konva `<Image>` с тем же `width × height`.
   - Пока ассет грузится или если `onerror` — рендерим прежний `<Rect fill={color}>`.
   - Спрайты лежат в `/public/sprites/...` и грузятся обычным HTTP (без bundler-чанков).

3. **3D — `useGLTF` из `@react-three/drei` + Suspense с Box-fallback**:
   - `<Suspense fallback={<BoxFallback ... />}><GltfModel url=... /></Suspense>`.
   - `BoxFallback` повторяет старую `boxGeometry`-репрезентацию — если модель не загрузилась или ещё не пришла, сцена остаётся валидной.
   - Дополнительный поворот `rotation` по Y и масштаб `scaleY` — чтобы подогнать координаты ассета (некоторые glTF имеют Z-up или нестандартный масштаб).

4. **Лицензии — только CC0 / CC-BY**, документируются в `LICENSES.md` с указанием автора, источника и SPDX-идентификатора.

5. **Lazy-loading**: и спрайты, и модели грузятся только когда мебель ставится на канву. Bundle для пользователей, не доходящих до Stage 3, не растёт.

### Альтернативы

- **Vector-sprites (SVG)** — отвергнуто: Konva не имеет прямой поддержки SVG-нод; нужна растровая конвертация. PNG проще.
- **OBJ вместо glTF** — отвергнуто: glTF — современный стандарт, поддержан `useGLTF` напрямую, поддерживает PBR-материалы, draco-сжатие.
- **CSG-вырез сложных форм** — отвергнуто: контроль выше, но требует сложной кодогенерации; выгоды нет, поскольку glTF делает то же декларативно.

### Последствия

**Плюсы:**

- Поэтапное обогащение каталога: ассеты добавляются по одному, без больших переработок.
- Bundle не растёт: ассеты вне основного пакета.
- Fallback гарантирует, что отсутствие ассета или ошибка загрузки не ломает приложение.

**Минусы:**

- Требуется отдельная работа по подбору и лицензированию ассетов (CC0 / CC-BY).
- glTF-модели могут добавлять ~100–500 КБ каждая — внимание к общему количеству.
- Возможна визуальная несогласованность (стиль спрайтов разных авторов) — отбираем ассеты со схожей стилистикой.

### Уточнение в спецификации

См. `docs/SPECIFICATION.md` §F15.
